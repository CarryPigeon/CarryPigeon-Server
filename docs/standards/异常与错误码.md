# 异常与错误码

**状态：草稿（待评审）**
**读者：** 写业务失败分支的开发者、对接错误语义的客户端
**边界：** 本文定义"失败怎么表达、码表放哪、怎么映射到 HTTP 与 WS"。端点清单见 `docs/api/HTTP接口.md`，实时错误帧见 `docs/api/实时通道协议.md`。

---

## 1. 分工

| 类型 | 含义 | 谁用 |
|---|---|---|
| `ProblemException` | 业务失败，对外可感知；状态码/原因/消息由注入的 `ProblemMapping` 决定 | 所有 feature |
| `InfrastructureException` | 基础设施执行失败（配置、JSON、ID、时间等） | `infrastructure-basic` 内部 |
| `RealtimeProtocolException` | 线上协议违规（信封非法、字段类型错） | 实时通道 |
| 校验异常 | 框架抛出的参数绑定/校验失败 | 由全局处理器统一转 422 |

`ProblemException` 不含任何业务语义与具体码值，新增错误码不需要修改基建。

---

## 2. `ProblemMapping` 契约

```java
public interface ProblemMapping {
    int status();      // 4xx/5xx 标准状态码
    String reason();   // 机器可读、客户端安全、跨协议一致
    String message();  // 面向客户端的默认文案，5xx 必须与内部细节无关
}
```

每个 feature 一个枚举实现它，放在 `domain/problem/<Feature>Problem.java`（例：`ChannelProblem`）。

## 3. `ProblemException` 工厂

| 工厂 | 用途 |
|---|---|
| `of(mapping)` | 使用码表默认消息 |
| `of(mapping, message)` | 覆盖对外消息（禁止泄露内部细节） |
| `of(mapping, message, details)` | 附带结构化明细（可序列化 Map） |
| `of(mapping, message, cause)` | 保留根因，仅用于日志链路 |
| `of(mapping, details)` | 明细 + 默认消息 |
| `of(mapping, cause)` | 根因 + 默认消息 |

读取器：`mapping()` / `status()` / `reason()` / `details()`。

## 5. HTTP 映射

统一入口：`shared/controller/advice/GlobalExceptionHandler`，响应用 `ApiErrorResponse{error: ApiError}` 包装：

```json
{"error": {"status": 422, "reason": "validation_failed", "message": "...", "requestId": "...", "details": null}}
```

`ApiError` 为 `NON_NULL`：`details`、`requestId` 为空时不输出。

| 异常 | status | reason |
|---|---|---|
| `ProblemException` | `mapping.status()` | `mapping.reason()` |
| 参数绑定/校验类（`MethodArgumentNotValid`、`BindException`、`ConstraintViolation`、`HttpMessageNotReadable`、`MissingServletRequestPart`、`MethodArgumentTypeMismatch` 等） | 422 | `validation_failed` |
| `HttpMediaTypeNotSupportedException` | 415 | `unsupported_media_type` |
| `HttpMediaTypeNotAcceptableException` | 406 | `not_acceptable` |
| `HttpRequestMethodNotSupportedException` | 405 | `method_not_allowed` |
| `MaxUploadSizeExceededException` | 413 | `payload_too_large` |
| `NoHandlerFoundException` / `NoResourceFoundException` | 404 | `not_found` |
| 其它 `Exception` | 500 | `internal_error` |

日志级别：`503` 记 `warn`，其它 5xx 记 `error`（带栈），4xx 记 `debug`。

## 6. WS 映射

实时通道不使用 HTTP 状态码，只把失败收敛成 `error.reason`（类型见 `docs/api/实时通道协议.md` §5）：

| 来源 | 下发 reason |
|---|---|
| `RealtimeProtocolException` 与信封非法 | `validation_failed` |
| `ProblemException`（如 `AuthProblem.AUTHENTICATION_REQUIRED`） | 该码表的 `reason`（`unauthorized`、`token_expired`…） |
| 未注册命令 | `unsupported_command` |
| 需要认证但未认证 | `unauthorized` |
| 未预期运行时异常 | `internal_error` |
| 空闲关闭 | `idle_timeout` |

**协议内部原因与对外原因不同**：`RealtimeFrameCodec` 内部用 `frame_invalid`、`type_blank` 区分具体校验失败，但对外统一为 `validation_failed`，内部原因只进日志。

## 7. 新增错误码

1. 在该 feature 的 `domain/problem/<Feature>Problem` 追加枚举常量，选定 `status/reason/message`。
2. 在抛出处用 `ProblemException.of(...)`；需要明细时传 `details`。
3. 更新 `docs/features/<feature>.md` 的错误码小节与本文 §4。
4. 新增 reason 时同步 `docs/api/`：HTTP 影响面写入错误表，WS 影响面写入 §5。

规则：

- `reason` 是**客户端契约**，一经发布不得改名；需要新语义就新增 reason。
- 5xx 的 `message` 必须与内部细节无关，禁止把异常消息直接透出。
- `details` 只放客户端可安全消费的结构化字段。
