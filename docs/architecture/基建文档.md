# 项目基建文档

## 1. 文档目的

本文只固化当前项目已经落地的基础设施能力与使用边界。

本文不扩展未确认的新基建设计，不替代架构文档、包结构规范与依赖引入规范。

## 2. 当前基建范围

当前已落地的基建重点在 `infrastructure-basic`，用于提供全局固定、长期稳定的基础设施能力。

当前已提供的能力包括：

- 统一日志基建
- 统一 ID 基建
- 统一 JSON 基建
- 统一时间基建
- 统一异常基建
- 统一启动检查契约
- 统一插件配置基建
- 基础自动配置与统一门面

`infrastructure-service` 当前仍只作为可拔插外部服务基建的承载目录，不在本文展开具体实现。

## 3. 模块定位

### 3.1 `infrastructure-basic`

- 负责固定基础设施能力
- 不承载业务规则
- 不承载数据库、缓存、邮件等外部服务实现
- 对上层提供稳定、简洁、可长期复用的基础能力

### 3.2 `application-starter`

- 负责装配与启动
- 提供当前最小运行配置
- 承接基础设施配置项
- 执行共享初始化检查
- 不承载 auth/user 仓储装配与 realtime 运行时等 feature 内部装配职责

## 4. 当前已落地的基建能力

### 4.0 AI 首轮阅读建议

如果阅读者是 AI 或第一次接触本仓库的开发者，建议优先建立以下心智模型：

1. `infrastructure-basic` 只承载**固定、全局、长期稳定**的基础设施能力。
2. 它不是数据库、缓存、对象存储等外部服务实现的容器；这些能力属于 `infrastructure-service/*-impl`。
3. 常用入口优先看：
   - `InfrastructureBasics`
   - `IdGenerator`
   - `JsonProviderImpl`
   - `TimeProviderImpl`
   - `PluginConfigurationProvider`
4. 启动阶段共享的初始化检查契约也属于固定编排基础设施，因此可放在 `infrastructure-basic`；但具体检查逻辑仍应留在相应 impl 模块。
5. 实际业务代码中，更常见的是直接注入具体 provider，而不是总是通过 `InfrastructureBasics` 门面访问。

### 4.1 日志基建

日志实现已统一为 `log4j2`。

当前日志配置文件：

- `infrastructure-basic/src/main/resources/log4j2-spring.xml`

当前日志目录规则：

- 默认输出到 `./service-logs`
- 可通过 JVM 参数覆盖：`-Dcp.log.home=/your/path`
- 可通过环境变量覆盖：`CP_LOG_HOME=/your/path`

当前日志保留规则：

- 活动 `.log` 文件不参与自动删除
- `.log.gz` 压缩归档默认保留 30 天
- 可通过 JVM 参数覆盖：`-Dcp.log.retention=7d`
- 可通过环境变量覆盖：`CP_LOG_RETENTION=7d`
- 清理动作只挂载在 `allFileAppender` 的 rollover 上，统一清理所有日志类型的过期归档，避免多个 appender 重复扫描目录

当前日志文件包括：

- `all.log`
- `debug.log`
- `info.log`
- `warn.log`
- `error.log`
- `error-json.log`

当前统一的日志上下文字段包括：

- `trace_id`
- `request_id`
- `route`
- `uid`

当前日志质量规则：

- HTTP 与 WebSocket 等线程边界应通过 `LogContexts.openScope()` 建立隔离作用域；进入时清除可能残留的线程上下文，退出时恢复调用方原有上下文。
- 写入 MDC 的值统一转为单行文本并限制为 512 字符；空值移除旧字段，避免线程复用时保留失效身份。
- HTTP / WebSocket 调试日志中的查询参数统一通过 `LogValueSanitizer` 处理；敏感参数名按 UTF-8 URL 解码后识别，token、password、secret、code、authorization、api key 等值必须遮蔽。
- 文本日志输出 logger name，不启用逐条调用者类位置解析；结构化错误日志包含 MDC 属性，但不额外计算 locationInfo。
- 文本与 JSON 文件统一使用 UTF-8；控制台仅在真实终端可用时保留 ANSI 样式。

约束：

- 日志基建属于固定基础设施能力
- 业务模块不应自行复制一套日志输出规则
- 日志上下文应优先复用 `LogContexts` 与 `LogKeys`
- 不可信文本写入日志前应复用 `LogValueSanitizer`，不得在 feature 内复制另一套敏感参数正则
- 当前滚动策略按日期和 100 MB 大小切分；归档保留按 `LOG_RETENTION` 执行，但部署侧仍需监控日志目录容量和 rollover 是否正常发生

### 4.2 ID 基建

项目统一使用雪花 ID。

当前实现：

- 基于 Hutool 雪花算法
- 对外能力由 `IdGenerator`、`IdUtil`、`InfrastructureBasics.ids()` 提供

当前配置项：

- `cp.infrastructure.id.worker-id`
- `cp.infrastructure.id.datacenter-id`

当前最小配置位于：

- `application-starter/src/main/resources/application.yaml`

约束：

- 整个项目的 ID 统一走该基建
- 不允许在业务代码中各自实现独立 ID 方案

### 4.3 JSON 基建

当前 JSON 能力由 `JsonProviderImpl`、`JsonUtil`、`InfrastructureBasics.json()` 提供。

职责：

- 提供统一序列化入口
- 统一全局 Jackson 行为
- 避免上层模块零散创建 ObjectMapper

约束：

- 业务代码优先复用统一 JSON 能力
- 若后续需要补充模块级序列化约定，应先评估是否仍属于全局固定能力

### 4.4 时间基建

当前时间能力由 `TimeProviderImpl` 与 `InfrastructureBasics.time()` 提供。

职责：

- 统一当前时间获取
- 为后续测试替换与时间语义收敛预留稳定入口

约束：

- 时间能力属于必要的基础设施能力
- 业务代码不应在各处散落时间格式规则

### 4.5 异常基建

当前基础异常能力包括：

- `InfrastructureException`
- `InfrastructureErrorCode`

职责：

- 表达基础设施层错误语义
- 为日志、配置、ID、JSON 等基础能力提供统一异常出口

约束：

- 基础异常只表达基础设施问题
- 不承载具体业务错误语义

### 4.6 启动检查契约

当前启动检查相关的固定共享能力包括：

- `InitializationChecker`
- `InitializationCheckResult`
- `InitializationCheckFailureException`
- `InitializationCheckRunner`

职责：

- 为启动层提供统一的初始化检查契约
- 让具体 impl 模块可以在不泄露自身实现细节的前提下参与启动检查
- 让 `application-starter` 只负责发现与执行检查，而不是直接耦合到数据库、缓存、存储等具体健康检查接口
- 必需检查应在独立监听器、长连接宿主或其他 `SmartLifecycle` 运行时启动前完成

边界：

- 这里只定义共享契约与失败语义
- 不在 `infrastructure-basic` 中实现数据库、缓存、对象存储等具体检查
- 具体检查实现应位于 `infrastructure-service/*-impl`

### 4.7 自动配置与门面

当前基础自动配置包括：

- `BasicInfrastructureAutoConfiguration`
- `IdAutoConfiguration`
- `JacksonAutoConfiguration`
- `PluginAutoConfiguration`
- `TimeAutoConfiguration`

当前统一门面：

- `InfrastructureBasics`

门面当前对外暴露：

- `ids()`
- `time()`
- `json()`
- `plugins()`

目标：

- 让上层模块使用固定基础设施时入口更清晰
- 避免直接依赖过多底层基础类

补充说明：

- `InfrastructureBasics` 适合表达“当前逻辑需要一组固定基建能力”的场景。
- 若某个类只需要单一能力，例如时间、JSON 或 ID，直接注入 `TimeProviderImpl`、`JsonProviderImpl`、`IdGenerator` 更清晰。

### 4.8 插件配置基建

当前插件配置基建包括：

- `PluginProperties`
- `PluginConfigurationProvider`
- `PluginAutoConfiguration`
- `InfrastructureBasics.plugins()`

当前统一配置入口：

- `cp.plugin.configs`

职责：

- 为后续插件提供统一配置绑定入口
- 表达插件级启停状态
- 承载由插件自身解释的 `options`
- 为上层模块提供只读查询能力

边界：

- 不实现插件加载、动态类加载、生命周期管理或插件市场
- 不解释具体插件 options 的业务语义
- 未配置插件默认视为未启用
- 具体插件配置只有在对应插件实现已经读取时才应写入运行配置

### 4.9 可替换服务端口真实性

`infrastructure-service/*-api` 的方法必须真实表达所有实现都需要满足的最小契约。

约束：

- 声明“原子消费”“按过滤条件查询”“写入”“更新”或“删除”的方法，不得用更弱的默认实现伪装完整能力。
- 不得以静默空列表、空 `Optional`、忽略过滤条件或运行时 `UnsupportedOperationException` 作为已被业务流程依赖的方法默认值。
- 需要兼容弱实现时，应拆出明确命名的可选能力或在装配阶段拒绝不完整实现，不能把失败延迟到业务请求。
- 语义完整的便利委托可以保留为 `default`，例如只改变调用形式但不削弱事务保证的重载；是否保留以可替换性和行为测试为依据，不机械禁止 Java 默认方法。
- 原子契约必须由具体实现使用后端原语实现，并通过 API 契约测试和实现测试共同锁定。

### 4.10 可替换外部服务运行边界

外部服务的超时和健康检查由对应 `*-impl` 拥有，不能下沉到 `infrastructure-basic`：

- `database-impl` 使用 JDBC 连接 5 秒、socket 30 秒、Hikari 取连接 10 秒和校验 5 秒的默认边界；健康检查固定执行只读 `SELECT 1`，不接受任意 SQL 配置。
- `cache-impl` 使用 Redis 建连 5 秒、命令 3 秒的默认边界。
- `storage-impl` 创建自身 MinIO HTTP 客户端，默认建连 5 秒、读写分别 30 秒；配置由 `cp.infrastructure.service.storage.*-timeout` 提供并在绑定时校验为正值。
- `mail-impl` 使用 SMTP 建连 5 秒、读写分别 10 秒的默认边界。

公共 service API 在进入具体客户端前承担稳定输入契约：对象键最多 1024 UTF-8 字节，必须是无控制字符、无空段、`.` 或 `..` 段的相对键；预签名 URL TTL 必须为 1 秒至 7 天的整秒；纯文本邮件命令限制收件人 320 字符、标题 255 字符、正文 100,000 字符，并禁止邮件头 CR/LF 注入。

理由：超时是具体客户端运行语义，输入限制是所有实现必须共同满足的公共契约。按此边界放置可避免 domain 依赖 SDK，也避免 `infrastructure-basic` 变成可替换服务配置的通用容器。

## 5. 当前配置项

当前已确认并实际使用的配置项如下：

```yaml
spring:
  application:
    name: CarryPigeonBackend

cp:
  plugin:
    configs: {}
  infrastructure:
    id:
      worker-id: 1
      datacenter-id: 1
```

补充：

- `spring.application.name` 用于定义当前运行时应用名
- `cp.plugin.configs` 用于承载已接入插件的统一配置；空 Map 表示当前没有插件配置
- `worker-id` 与 `datacenter-id` 当前取值范围均为 `0..31`
- 多节点部署时必须保证节点取值不冲突

## 6. 当前包落点

`infrastructure-basic` 当前包结构如下：

```text
team.carrypigeon.backend.infrastructure.basic
├── config
├── exception
├── id
├── json
├── logging
├── plugin
├── startup
├── time
└── InfrastructureBasics
```

说明：

- `config`：基础自动配置与配置前缀支持
- `exception`：基础设施异常与错误码
- `id`：统一 ID 能力
- `json`：统一 JSON 能力
- `logging`：日志上下文与日志键
- `plugin`：统一插件配置绑定与查询入口
- `startup`：启动检查共享契约、结果模型与执行器
- `time`：统一时间能力

## 7. 使用约束

- 固定基础设施能力优先从 `infrastructure-basic` 获取
- 可替换外部服务能力不得塞入 `infrastructure-basic`
- `chat-domain` 可以依赖固定基础设施能力，但不得依赖任何外部服务实现
- `application-starter` 负责最终装配，不负责承载基础规则实现
- `application-starter` 可执行共享初始化检查，但不应直接承载数据库、缓存、对象存储等检查实现
- 具体健康检查实现位于 `infrastructure-service/*-impl`，而不是 `infrastructure-basic`
- 插件配置可以复用 `cp.plugin.configs.<plugin-id>`，但具体插件运行时与业务语义不得下沉到 `infrastructure-basic`
- 若存在 WebSocket、Netty 等独立监听器，其默认暴露策略应保守，且握手阶段需显式鉴权，不能仅依赖 HTTP MVC 拦截器

## 8. 当前状态结论

当前基建已经形成第一版可运行骨架，重点能力已覆盖：

- 日志
- ID
- JSON
- 时间
- 异常
- 插件配置
- 自动配置

但当前仍属于重写阶段的基建第一版，后续若新增数据库、缓存、邮件等能力，应进入 `infrastructure-service`，并继续遵守既定模块边界与依赖规则。
