# 整体架构

## 1. 模块划分与职责

```text
Backend（Maven 多模块，Java 21）
├── chat-domain               业务核心，按 feature 组织
├── infrastructure-basic      固定基建（无外部服务依赖）
├── infrastructure-service    可替换外部服务基建
│   ├── database-api / database-impl  关系型数据库
│   ├── cache-api    / cache-impl     缓存实现
│   ├── storage-api  / storage-impl    文件存储实现
│   └── mail-api     / mail-impl       邮件服务实现
├── application-starter       启动与运行时装配
└── distribution              分发产物（thin jar + lib + 脚本）
```

依赖方向：

```text
                    ┌───────────────────────────┐
                    │     application-starter   │
                    └───────┬───────────┬───────┘
                            │           │
              ┌─────────────▼──┐   ┌────▼─────────────────────┐
              │  chat-domain   │   │ infrastructure-service   │
              └───┬────────────┘   │        /*-impl           │
                  │                └────┬─────────────────────┘
        ┌─────────▼─────────┐           │
        │infrastructure-basic│◄─────────┘
        └───────────────────┘
```

## 2. `chat-domain`：整洁架构设计

### 2.1 一级结构

```text
team.carrypigeon.backend.chat.domain
├── features/     业务能力，按业务域切分
├── shared/       跨 feature 的协议与领域共享件
└── config/       跨 feature 的接入策略与运行时机制（http / server / ws）
```

### 2.2 feature 内分层

标准形态（以 `channel` 为基准）：

```text
features/<feature>
├── domain/            业务内核，不依赖任何出站实现
│   ├── api/<capability>/{*Api.java, input/, result/}  对controller层即其他feature暴露的地方
│   ├── model/         数据模型
│   ├── repository/    仓储抽象（业务语义）
│   ├── service/<capability>/*DomainApi.java   业务代码的具体实现，只能依赖基建、springboot以及该feature代码
│   ├── capability/    域内需要的、非持久化的外部能力抽象
│   ├── extension/     （可选）域内扩展点，由本 feature 的 support/ 实现
│   └── problem/       本 feature 的错误码表
├── adaptor/           唯一出站包：把外部能力实现成 domain 的抽象
│   ├── persistence/   → database-api
│   ├── realtime/      → infrastructure-basic 的实时事件发布契约
│   └── user/          → 其它 feature 的 domain/api
├── controller/http/   HTTP 入口；本层 DTO 固定在 controller/http/dto
├── support/           （可选）无外部依赖的技术实现，只服务本 feature
└── config/            （可选）本 feature 的局部装配
```

七个非 `channel` feature 已按同一形态收敛：`api/<capability>` 与 `service/<capability>` 的子域一一对应，
`input/` 同时承载 `*Command` 与 `*Query`，`result/` 承载 `*Result`；不再有 `domain/command`、`domain/query`、
`domain/projection` 这类按技术职责切的包。当前保留 `support/` 的只有三处，且都无外部依赖：
`auth/support/security`（Argon2、HMAC JWT、SHA-256）、`plugin/support/message`（内置消息插件实现）、
`verification/support/verification`（内存与缓存两种验证码能力）。

依赖方向：

```text
controller ──> domain/api ──> domain/service ──> domain/repository（接口）
                                     │                  ▲
                                     ▼                  │
                              domain/capability      adaptor/persistence
                                     ▲
                                     │
                              adaptor/{realtime,user,...}
```

硬约束：

- `domain` **不得** import `adaptor`、`controller`、`config`、`support`，也不得 import 其它 feature 的任何包（除 `domain/api`）。
- `adaptor` 只实现 `domain/repository` 或 `domain/capability` 定义的抽象，不得反向被 `domain` 依赖。
- `controller` 只做协议转换，不承载业务规则；业务失败的表达统一走 `domain` 的错误码。

> `domain` 里只写**抽象**（我需要什么能力）；`adaptor` 里只写**实现**（这个能力具体怎么接外部）。
> `adaptor` 的存在条件是该能力有外部依赖；纯内存计算或纯规则不需要 `adaptor`。

### 2.4 两条典型调用链（`channel` 为基准）

**HTTP 同步查询**

```text
ChannelController(controller/http)
  → ChannelQueryApi(domain/api)              ← 只依赖契约
    → ChannelQueryDomainApi(domain/service)  ← 实现契约
      → ChannelRepository(domain/repository)  ← 抽象
        ← DatabaseBackedChannelRepository(adaptor/persistence)  ← 实现，走 database-api
```

**写操作 + 提交后推送**

```text
ChannelDomainApi(domain/service)
  → TransactionRunner(infrastructure-basic)  ← 固定基建事务契约
      → 事务体内写仓储
      → afterCommit: ChannelEventNotifier(domain/capability)
          ← RealtimeChannelEventNotifier(adaptor/realtime)  ← 实现，翻译成线上事件
              → RealtimeEventApi(infrastructure-basic)       ← 实时通道发布契约
                  ← RealtimeEventPublisher(config/ws/downlink) ← 实现，编码 + 落窗口 + 广播
```

这条链是"业务不依赖传输"的关键：`channel` 只知道"提交后要通知某人"，不知道 Netty、不知道 JSON、不知道帧格式。

### 2.6 装配约定

- **组件直接标注 `@Component`**，不写 `@Configuration` + `@Bean` 装配类。
  需要条件装配时用 `@ConditionalOnProperty`（例：`database-impl` 的全部 `MybatisPlus*DatabaseService` 受 `cp.infrastructure.service.database.enabled` 控制）。
- **不可变配置记录**用 `@ConfigurationProperties` + 启动类的 `@ConfigurationPropertiesScan` 绑定，**不标 `@Component`**（组件扫描无法为记录做构造器绑定）。
- **Mapper 接口**由启动类上的 `@MapperScan` 统一扫描；`*-impl` 不为此保留配置类，也不再有 `META-INF/spring/...AutoConfiguration.imports`。
- `@Configuration`/`@AutoConfiguration` 只保留给"需要装配第三方类型"的场景，当前只有 `storage-impl`（`MinioClient`、`OkHttpClient`）。

## 3. `infrastructure-basic`：固定基建

```text
infrastructure.basic
├── config/       配置基础工具
├── exception/    ProblemMapping、ProblemException、InfrastructureException
├── id/           IdGenerator（雪花）
├── json/         JsonProvider + 全局 Jackson 约定（snake_case）
├── logging/      LogContexts、LogKeys、日志值清理
├── plugin/       插件配置读取 + 插件清单与宿主身份校验
├── realtime/     实时通道契约：codec + downlink/ + uplink/
├── startup/      初始化检查契约、结果模型、执行器
├── time/         TimeProvider
├── transaction/  TransactionRunner + Spring 适配
└── event/        提交后事件发布桥接
```

## 4. `infrastructure-service`：可替换外部服务

每个外部服务固定拆成两个模块：

```text
{service}-api   ← chat-domain 只依赖这一层
├── service/    服务接口（数据库默认为表级元能力）
├── model/      表行模型；跨表读模型例外需明确标注
├── health/     健康检查契约
└── exception/  该服务的领域无关异常

{service}-impl  ← 只有 application-starter 依赖
├── config/     *Properties（含 enabled 开关），不放装配类
├── jdbc/ mybatis/ ...  具体驱动与持久化实现
├── health/     健康检查实现
└── startup/    初始化检查实现（实现 infrastructure-basic 的 InitializationChecker）
```

规则：

- `*-api` 不依赖任何 `*-impl`，也不依赖 `chat-domain`。
- `*-impl` 只依赖自身的 `*-api` 与 `infrastructure-basic`，**不得依赖 `chat-domain`**。
- 实现类一律 `@Component`（必要时叠加 `@ConditionalOnProperty` 读开关），由 `application-starter` 的组件扫描装配；
  只有需要装配第三方类型时才补 `@AutoConfiguration` + `@Bean`（当前仅 `storage-impl`）。
- 开关统一为 `cp.infrastructure.service.<service>.enabled`，由 `*-impl` 组件类上的 `@ConditionalOnProperty` 读取。
- 启动期检查由 `*-impl` 提供实现，由 `application-starter` 统一编排执行。
- `database-api` 默认只提供表级元能力；搜索与跨表读模型按 `docs/standards/持久化与SQL.md` 的例外规则处理。

## 5. `application-starter`：启动与装配

```text
starter
├── ApplicationStarter.java      启动类（@SpringBootApplication + @ComponentScan + @ConfigurationPropertiesScan + @MapperScan）
├── PluginPreflightCommand.java  插件预检 CLI 入口
├── bootstrap/plugin/            插件预检、就绪门禁、启动时序
├── config/http/                 本地开发 HTTP 调试开关
├── config/initialization/       初始化检查编排配置
├── config/openapi/              OpenAPI 分组、命名策略、错误响应、请求示例
├── config/plugin/               插件运行时装配
└── support/http/                请求日志过滤器、插件启动门禁过滤器、就绪探针
```

## 6. `distribution`：分发产物

```text
dist/
├── app/       application-starter thin jar
├── lib/       全部依赖 jar
├── config/    application.yaml（外部可覆盖）
├── plugins/   插件 jar
├── bin/       启停脚本
└── logs/      运行期日志（由应用创建）
```

- 产物格式：`dir` 与 `zip` 两种。
- 配置覆盖：`config/application.yaml` 与 JVM 属性/环境变量共同生效，优先级由 Spring Boot 标准规则决定。
