# WebSocket 短期事件缓冲与恢复方案

状态：待实现。本文记录当前代码、已明确需求和暂定方案，供后续继续开发和审核；文中的目标行为不代表当前代码已经具备。

## 背景与目标

- 客户端断线重连后，可以补拉断线期间错过的短期事件；事件最多保留两分钟。用户已接受数据库事务提交与进程内事件写入之间极短的不一致窗口，也接受服务重启或游标失效后重新读取业务状态。
- 事件按接收范围隔离，既支持频道成员共同接收的事件，也支持只发给指定账号的事件。它应能支持消息撤回及其他不方便直接重新拉取的信息。
- 频道之间不应因共用事件队列、锁或单一容量上限而互相挤占；查询不应扫描其他频道的事件。
- 已过期事件需要主动清理，空闲时也不能无限期占用内存。
- 消息自行撤回应限制在发送后两分钟内。管理员治理是否遵守相同时限尚未确定，不要自行改变现有管理员权限。
- 遵循仓库 `AGENTS.md`：业务规则在业务层，协议表示在各自协议边界；不要为了复用引入无必要的框架；目前未经用户新要求不新增测试类，不提交代码。

## 当前代码与不足

- `chat-domain/.../features/message/adaptor/realtime/ChannelEventBuffer.java`：当前为单进程内存队列，所有频道共用锁、序号和 10,000 条总上限。读写时才惰性清理两分钟前的事件；读取通过遍历全局队列筛选频道。它目前只保存频道 ID、消息 ID 和消息事件类型。
- `.../features/message/adaptor/realtime/RealtimeMessageEventNotifier.java`：消息创建和撤回在事务提交后先写缓冲，再通过 `RealtimeEventApi.publishToChannel` 推送。提及和已读状态通过账号定向推送，但没有写入短期缓冲。
- `.../features/message/controller/http/MessageChangeController.java`、`.../domain/api/change/MessageChangeApi.java`：当前仅提供消息变更的频道 HTTP 补拉。省略游标时返回当前事件位置及空列表；携带游标时读取之后的事件。游标由客户端保存，而非服务端按用户保存。
- `.../domain/service/message/MessageChangeService.java` 已通过领域 `MessageChangeReader` 接口访问缓冲，`.../adaptor/realtime/InMemoryMessageChangeReader.java` 完成具体缓冲数据转换；不要重新引入领域层对 WebSocket 实现或配置包的直接依赖。
- `.../domain/service/message/ChannelMessageService.java` 的撤回逻辑已校验频道成员、操作者权限和撤回状态，尚未校验发送后两分钟。`ChannelMessageContextService.getMessage` 已支持按频道和消息 ID 查询当前消息。
- `infrastructure-basic/.../realtime/downlink/RealtimeEventApi.java` 与 `chat-domain/.../config/ws/downlink/RealtimeEventPublisher.java` 是现有推送入口。当前账号定向 `publish` 会生成自己的事件 ID 和时间；要让推送与补拉共用事件 ID，需要检查并调整现有接口和投递路径，不能假设其已经支持。
- 当前只实现消息变更，不是通用事件恢复；两分钟是最大保存时间，全局容量可能提前截断事件。当前没有针对事件缓冲和断线恢复的现有测试。

## 暂定方案

### 按接收对象划分事件流

采用共用的短期缓冲实现，但以类型和业务 ID 标识各自独立的流：

| 流 | 首批事件 | 授权边界 |
| --- | --- | --- |
| 频道流 | 消息创建、消息撤回 | 补拉时校验当前账号对频道的访问权限 |
| 账号流 | 提及通知、个人已读状态更新 | 只能读取当前认证账号自己的流 |

事件包含事件 ID、流内序号、事件类型、产生时间和业务载荷。频道消息事件继续只携带频道 ID、消息 ID，不缓存正文；其他事件的载荷和数据可见性由对应业务确定。不要把定向事件直接写入成员共享的频道流，也不要把所有数据统一变成消息专用结构。

发布方在业务事务提交后写入相应流，再推送同一事件。WebSocket 和 HTTP 可使用各自协议表示，但同一事件的 ID、类型和语义应一致。先核对现有 WebSocket 帧及客户端契约，明确新增序号、账号事件和数据表示的影响；不为 HTTP 复用而引入公共协议 Mapper。

同一流写入时原子分配序号、记录事件，读取保持序号顺序。推送可能因并发而乱序，客户端不能用最大推送序号跳过补拉；应按事件 ID 去重，并只在按序应用补拉结果后保存游标。账号与频道事件若指向同一业务变化，应明确它们是两个独立事件还是同一事件的多份投递，不能无意中产生语义重复。

### 游标与 HTTP 恢复

- 客户端为每个流分别保存服务端返回的游标。游标应绑定流类型、流 ID、服务实例和流生命周期，并包含恢复位置与有效期所需信息；游标属于 HTTP 协议边界，不应成为 WebSocket 私有实现类型。
- 省略游标时返回空事件列表和请求时的当前位置。客户端先获取该位置，再读取对应业务状态，之后使用游标补拉期间发生的变更；快照与事件可能重叠，客户端按事件 ID 去重并以业务当前状态处理。
- 带游标时读取该流中其后的事件并分页；返回下一游标和是否有更多事件。未读完分页时不能通过连续翻页延长原始恢复窗口，空页也要返回可继续使用的游标。
- 实例变更、流生命周期变更、超时或游标之后发生截断时，明确返回 `410`，要求重新获取当前位置及相关业务状态。无效格式使用项目已有输入错误模型；不能静默返回不完整数据。
- HTTP 接口拟从消息专用 `/api/channels/{channelId}/message-events` 调整为频道事件和当前账号事件各自的恢复入口。具体路径、响应结构、旧接口是否移除及客户端改动需在实现前核对；用户此前表示不需要默认兼容，勿自行增加双读双写。

### 容量、隔离与过期清理

- 每条流拥有自己的队列、序号和并发控制，读取只访问目标流；单流容量限制仅截断该流的事件。单流上限、载荷大小及定时周期需要依据目标负载和实际可用内存确定，不直接沿用当前全局 10,000 条作为保证。
- 设置进程级内存保护，限制大量活跃流带来的总体占用。明确达到上限时的处理策略、受影响流的截断标记和观测方式；不得为了让另一条流写入而让旧游标静默漏数据。
- 两分钟是事件的最长保留时间。任何有限容量都可能导致提前截断；如要保证特定负载下保留两分钟，应结合吞吐、事件大小和可用内存计算容量。
- 使用统一的周期任务主动清理；读写目标流时也检查过期，确保定时任务尚未运行时不返回过期事件。正常空闲时物理移除可能延迟一个清理周期，应用停止后进程内数据随进程释放。
- 清理队列时保留足以判断有效游标是否遗漏事件的截断信息；空流及相关记录只在不会让仍有效的旧游标误判为完整时移除。删除、重新创建流与并发写入必须协调；重新创建时更换生命周期标识，不能重用导致旧游标误读。
- 首先使用简单的周期清理；只有观测表明遍历大量流的成本成为瓶颈时，再评估按到期时间组织的清理结构。

### 消息撤回时间

暂定发送者只能在消息发送后**未满两分钟**时自行撤回，达到两分钟则拒绝；使用项目现有 `TimeProvider` 和消息发送时间，在业务权限校验及数据库更新流程内检查，并使用明确的项目业务错误。确认重复撤回的幂等行为和时间边界后再落地。

现有代码允许有权限的管理员撤回成员消息。**管理员是否也受两分钟限制尚待用户明确**；不能因为缓冲保留期为两分钟就擅自改变治理规则。管理员可撤回更早消息与事件缓冲时长并不矛盾：缓存的是撤回发生时产生的事件。

## 尚需确定的规则和实现细节

1. 管理员撤回时限；频道成员加入前的频道事件能否补拉；成员退出或被移除后，账号流中的历史提及应如何展示及授权。
2. 频道流与账号流具体 API 路径、WebSocket 帧格式、游标格式和客户端重连流程；既有消息专用接口的替换范围。
3. 提及、已读状态各自的恢复载荷与补拉失效后的刷新方式，以及其他事件是否确实需要接入，避免为了通用而提前抽象。
4. 单流容量、全局内存上限、清理周期、事件载荷上限与容量保护策略；无负载依据时不能承诺两分钟内所有事件均可恢复。
5. 同一账号多个连接、不同流的顺序和重复事件的客户端处理；明确本方案只保证单流内部的恢复顺序，不承诺跨流顺序。

1. 重新阅读当前事件发布、频道权限、消息撤回、时间源、HTTP 错误与 WebSocket 协议代码，确认待定产品规则和现有未提交改动。

3. 通过领域能力及适配器连接业务发布和读取；确保账号及频道推送使用与补拉一致的事件身份和内容，接入消息、提及及已读状态。
4. 实现受权限约束的频道和账号补拉入口，处理原消息专用 API 和对应 DTO；调整客户端所需的协议描述。
5. 在消息领域服务落地已确认的撤回时间规则，不扩展未确认的管理员规则。
6. 按改动范围编译并执行已有测试；未经新要求不新增测试类。以适当的运行或临时验证检查：跨流隔离、账号数据不泄露、并发顺序、分页、断线恢复、两分钟边界、提前截断、空闲清理、流重建和实例重启。明确报告哪些验证实际完成，不能用编译代替行为验证。

## 已接受的边界

这是单进程内存方案，不提供持久化或跨实例事件共享。服务重启、切换实例或异常退出后，客户端应重新读取业务状态；数据库提交后、内存事件写入前如果进程终止，事件可能丢失。缓冲写入或推送失败的处理与日志应区分，不能把进程内缓存描述为可靠消息队列。
